# SMS export rollout

The CMD API queues SMS selection and export work. The app polls JSON status endpoints. Export files are retained on CMD runner's private storage; a ready status returns a 15-minute signed direct CMD download URL, so CSV/ZIP bytes do not pass through the report proxy.

For hosts upgrading from the existing asynchronous SMS release, this patch adds no migrations. Keep the package on Composer dev-dev; this patch changes no Composer files. After promoting the package feature branch into dev, update the package, clear application caches, and restart the queue worker gracefully. Deploy the corresponding app feature branch. New requests save checkpoints between batches. Requests from the previous worker have no saved completed result to recover.

Before enabling exports on CMD runner:

1. Keep `oduaildr/liberty-cmd-package` on `dev`. Publish `reports-sms-migrations` and apply the two new `2026_10_07_*` migrations to `sqlsrv`. Do not rerun or drop the existing SMS tracking migration.
2. SMS exports default to `storage/app/private/sms-exports`, created automatically under CMD runner's existing writable storage. No bucket or new environment setting is required. Keep `APP_URL` as CMD runner's direct HTTPS origin; this existing setting is used for signed download links. Retain this directory across deployments and server replacements, include it in the host's backup policy, and do not add automatic cleanup. Local storage is tied to this server; moving to multiple hosts requires shared persistent storage. The package does not modify Composer. Older S3 artifact keys continue to use the existing S3 bucket/region and presigned downloads. Optional `CMD_SMS_EXPORT_DRIVER=s3` retains the old publishing behavior.
3. Keep the existing `tu-export` worker running. This job allows one attempt and up to 7,000 seconds. CMD runner must use its database queue with `DB_QUEUE_RETRY_AFTER` above 7,000 seconds, and the worker timeout must exceed the job timeout. The API fails closed when the queue reservation is too short. Otherwise the status can remain queued or show a worker failure. Avoid running another export for the same drops until reconciliation.
4. Run `php artisan optimize:clear` after changing config. Check `GET /api/cmd/mail-drop-export-report/preview?page=1`, then queue a small selection and export through the app before a large production request.

`POST /api/cmd/mail-drop-export-report/selection` accepts a UUID `request_id` and either `target` or `drop_pks`; it returns 202. Poll `GET /api/cmd/mail-drop-export-report/selection-status?request_id=...` for `ready`, `drops`, `total`, and `shortfall`. `POST /api/cmd/mail-drop-export-report/export` accepts a UUID `request_id`, `target`, and optional `drop_pks`; it returns 202. Poll `GET /api/cmd/mail-drop-export-report/export-status?request_id=...` until `ready` and open `download_url` directly. Reusing the same request ID with different inputs is rejected. Requests and download links are scoped to the CMD user's email.

An export copies its completed CSV/ZIP into a private request directory, verifies its size and SHA-256 hash, flushes it, and atomically publishes the file and manifest before the SQL transaction records SMS drop use. New Linux directories/files retain the existing storage group's read access for separate worker and web identities; permission assignment is verified before publication. Final artifacts are retained when worker scratch files are removed. A failed generation or publication rolls back SMS tracking. If tracking exists but a file cannot be verified, status is `needs_reconciliation`; do not automatically export those drops again. Ready-status polling checks the small manifest and file size; publication, recovery and direct download perform full hash verification. Direct downloads require a valid expiring signature, a ready request, matching recorded SMS tracking, and a verified file/manifest. Retain local artifacts and older S3 objects until the business sets a retention policy. Removing them would remove the downloadable copy of a recorded export. Private local storage avoids the S3 upload step; it does not affect SQL selection speed or guarantee protection from loss of the host's disk.

Automatic selection preserves the existing fewest-use priority. It accumulates whole drops in sequence. An exact target stops immediately. When the next drop would exceed the target, it retains the subtotal below the target and inspects the next 30 candidates in sequence. The final drop is the smallest qualifying improvement in the same SMS_Drops use-count band; ties keep the first candidate. If no candidate improves the fit, the original crossing drop is retained. A higher-use drop cannot bypass a lower-use crossing drop. The frozen marketing list prevents concurrent export counter changes from moving pagination during counting. Eligibility is checked again at export time.

Targets and tracking count eligible phone numbers, not CSV lines: a row can contain up to five phones, and an additional row retains any sixth phone. Any positive exact integer target is accepted up to the JavaScript safe-integer maximum, 9,007,199,254,740,991. The former ten-million-phone and 500-drop caps are removed. Shortfalls are reported when the available inventory cannot meet the target. Database count/target columns already use BIGINT.

CSV splitting is disabled by default, so all selected records are written to one streamed CSV regardless of the row count. The existing CSV part-limit/ZIP code is retained. Setting CMD_SMS_EXPORT_SPLIT_CSV=true deliberately enables that optional capped-part path. Existing ZIP artifacts still download normally.

Selection now counts normalized phones inside SQL Server without looking up names, addresses or debt for each lead. The asynchronous worker counts one whole drop per job, records its completed count and the frozen candidate order in the existing selection request Result, then queues the next batch. A retry uses the same request ID and resumes saved completed drops. Counts are never treated as export history; source eligibility is checked again when exporting. No additional schema migration is needed for checkpoints. Actor-scoped local file snapshots serve polling requests without another Azure query; throttled SQL progress remains the fallback. The app displays a progress bar for phones toward the target (or chosen drops in manual mode), then a separate next-30 final-drop check. It shows actual eligible-phone counts, processed drops, current drop and elapsed time, retries temporary status errors for the same request, and limits each status wait to eight seconds. Progress advances after each whole drop; one large drop may still take minutes. Each count temporarily allows up to 1,800 seconds for that SQL statement, below the queue job limit, and restores the prior connection timeout afterwards. A failed request remains visible with Resume saved batches and Clear failed selection actions. A worker completion regression test verifies that queued/running query filters cannot suppress the final ready update.

Read-only Azure verification on 2026-10-08: the optimized one-million selection path found 1,000,030 eligible phones across 193 selected drops in 87.39 seconds before the next-30 refinement; the previous request had Target=1,000,000 and a 16m37s worker log, but its ready update was lost. These are separate runs with current database/load conditions, not a guaranteed completion time. A real source-drop row stream matched the SQL counter at 43,790 eligible phones but took 214 seconds. A later three-million selection benchmark hit a 300-second SQL timeout while counting a batch containing millions of historical source rows. After switching to one-drop queries, the largest drop in that batch (LTIWCO3560A, 2,062,950 source rows) completed a read-only count of 61,323 eligible phones in 98.133 seconds. Existing drop-name indexes require millions of heap lookups to read phones. The new one-drop jobs reduce wasted lookahead work and preserve progress across jobs; they do not prove a fixed completion time or remove that database I/O cost. Large CSV generation speed and the authenticated API Gateway path are not proven by the earlier count benchmark. Cached-controller polling averaged 1.563ms over 100 local checks with zero SQL queries; this excludes network/authentication time.

Focused regression checks cover whole-drop selection/refinement, synced-contact suppression, identity/debt conflicts, rollback and request replay, large manual lists, single-CSV record preservation, optional ZIP splitting, local artifact retention/checksum validation and signed download protection. Ten SELECT-only SQL Server fixture cases are opt-in through CMD_SMS_SQLSERVER_READ_ONLY_TESTS=1 using a bootstrapped host; they create no tables or tracking records. Linux worker/web shared-group read access and a complete live signed download still need a server smoke check. Local artifacts must remain in the existing host backup plan; private local storage does not survive host-disk loss by itself.
